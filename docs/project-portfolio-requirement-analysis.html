结论（先看这里）

  • 是好方案：对「多业务线、多专项、主管兼管」的组织，大项目 → 大任务 → 子任务 是刚需；否则任务会堆成扁平列表，列表、日报、改派、查询都会难用。
  • 要克制：你们是「任务规划 + 承接 + 催办」平台，不是 完整项目管理系统（PRD 已写明不替代 CAPA/项目管理系统）。应做 轻量项目目录 + 分组 UX + AI 建议归属（可改），而不是甘特、预算、里程碑全套。
  • 需求普适；机器人自动判断项目 值得做，但必须是 建议 + 用户确认，不能静默写死。

1. 在项目管理里，这是不是好方案？

对用户场景：好

用户诉求没有「项目」时有「项目」时
管多个大方向（管线、注册、质量专项等）只能靠标题关键词、个人记忆天然分桶、筛选、汇总
机器人理解上下文易与其它任务混在一起「在 XX 项目下」约束检索与拆解口径
主管工作台单列表 + 关注状态（现网）按项目看 KPI、阻塞、待办
员工视角「我有多少活」「我在哪些项目里各有多少活」
与 PRD 的关系 PRD 逻辑模型里 PlanDraft 已有「产品/项目引用」字段，但现网 SQLite tasks 表尚无 project_id，历史任务列表也是扁平的。用户反馈等于把「弱引用」升级为一等公民，方向正确。

对产品边界：要克制

适合做不适合首期做
项目档案（名称、简述、负责人、状态）；任务归属；筛选/报表；AI 推荐归属 跨项目 WBS 依赖、项目级资源负荷、挣值、版本基线、与 Jira/MS Project 双向同步

若用户说「只用我们平台管多个大项目」，应理解为协作与执行中枢，不是计划编制与 PMO 全套。

2. 普适吗？

需求层面：普适。 多项目组合（Portfolio）+ 项目内工作包，在 PMBOK、敏捷、质量事件管理里都很常见。

解决方案层面：要分层，不能一种 UI 打天下。 需要和用户澄清两个概念（避免建错模型）：

  1. 「大任务」 是否 = 你们已发放的一条正式任务（含多条子任务）？—— 多数情况应是。
  2. 「大项目」 是长期容器（数月～年），还是短期专项（几周）？—— 可用同一「项目」实体，用状态/类型区分。
例外 一次性行政杂项、跨项目协调会，应允许「未归类 / 临时」或「跨项目」标签，否则用户会反感强制分类。

3. 建议的三层模型（与现网对齐）

大项目（Project） ← 用户说的「大的项目」、业务线 / 专项
  └─ 大任务（Task） ← 一次 publish 的正式任务包（现网 taskNo + planId）
      └─ 子任务（Subtask） ← 现网 WBS 行，承接 / 催办粒度

域（质量/研发） 与 项目（业务归属） 应正交：任务可同时有「域」+「项目」，不要混成一个下拉。

4. 与现网平台的牵涉

层级现网加「项目」后牵涉
数据 tasks：planId、title、manager… projects 表 + tasks.project_id；发布、改派、通知、进展推送都要带项目
会话 taskScopes = 同聊多条规划线，≠ 组织项目 需 activeProjectId 或 publish 时绑定；与 start_new_task 纪律一致
Agent knownFacts、search_similar_plans 项目描述进注册表；分类用专用 tool，优于纯 prompt 猜
工作台 历史任务扁平列表 项目切换、列表分组、面包屑、筛选记忆
权限 主管白名单 项目可见范围；admin 跨项目
报表 每日进展按主管聚合 按项目切片

5. 机器人「帮填属于哪个大项目」

是好方案，但必须：建议 + 确认，不能静默写死。

推荐流程

  1. 项目注册表（主管维护）：名称 + 一两句描述 + 关键词/别名 + 可选负责人。
  2. 新需求进入时（CLARIFY 末尾或 DRAFT 前）：模型 list_projects + suggest_project，返回 Top3 + 置信度 + 理由。
  3. 回复写明：「建议归入：A（理由…）；也可选 B / 新建 / 暂不归类」。
  4. 用户纠正（如「这是注册申报那个」）→ 写入 knownFacts + draft / session 默认项目。
  5. 发放前：prepare_publish 校验；试点可「强烈建议」，成熟后可配置「必选项目」。

不建议

  • 只在任务 title 里塞项目名（查询、统计、深链都会烂）。
  • 100% 自动归类且无纠正入口（误归类比未归类更伤信任）。
  • 用 search_similar_plans 代替项目表（相似历史 ≠ 组织归属）。
两者可并存 先定项目，再在项目内搜相似历史计划。

6. 只用本平台管多项目 · UX 要点

应 项目优先（project-first），而不是任务优先再筛选：

位置建议
主管首页项目卡片/侧栏（进行中、待您处理、阻塞）→ 点进项目再看任务
钉钉 / 规划助手显示当前项目 chip；支持「切换到 XX 项目」「新建项目」
默认项目记住本次会话默认，减少每条都问
列表项目内筛选 + 全局「全部项目」；保留关注状态排序
员工端按项目分组；通知带项目名
查询话术「注册项目下有哪些任务」→ list_managed_tasks 带 projectId
新建项目对话里一句「新建项目：OCT 上市」完成，勿逼用户去别的系统

会话：主线程可共用，但每条 publish 绑定 projectId；或大专项用侧会话（与现有 thread=side 策略要在产品层写清）。

7. 风险与要拍板的规则

风险缓解
与 Jira/QMS 双轨预留 externalRef；首期只做展示，不同步
历史任务无项目「未归类」+ 引导补全；不阻塞改派/催办
AI 误归类置信度阈值 + 发放前确认 + 审计 project_source: user/ai
权限泄露项目 ACL；列表只返回有权限项目
范围膨胀MVP：CRUD 项目、绑定、筛选、suggest；不做项目甘特

建议产品拍板

  • 是否强制每条正式任务必选项目？（建议：试点「强烈建议」）
  • 一人是否参与多项目？（几乎一定是）
  • 项目谁可建？（主管 + admin；员工只读）

8. 分期建议

MVP
项目实体 + 工作台/列表按项目筛 + publish 写入 + 助手展示当前项目 → 解决「多项目堆在一起」
MVP+
suggest_project + knownFacts + 发放前确认 → 满足「机器人帮填」
V1.2
进展推送/催办按项目汇总；员工视图分组 → sole-platform 可日报
V2+
项目级指标、跨项目资源视图（仍不做完整 PM）

9. 两个直接问题的答案

问题答案
在项目管理里是好方案吗？ 是。 对多业务线主管是刚需；在你们定位下属于「导航与上下文层」，不是范围蔓延的借口。
是普适的需求和解决方案吗？ 需求普适； 方案要轻量、可纠错、与任务/子任务分层一致。机器人判断项目 普适且值得做，形态应是智能推荐 + 显式确认 + 可改。

本地打开：用浏览器直接打开本文件，或从项目根目录访问 docs/project-portfolio-requirement-analysis.html。

若需落 PRD/FR 或实现，可在对话中说明项目数量、是否已有外部项目清单要对齐。
