现网四 Bug 修复说明

2026-05-26 · 说明本次要改什么、改完用户侧会看到什么 · 对应开发计划「现网四 Bug 修复」

一句话

让员工在钉钉内就能打开任务、登录页不再像测试页、主管在草案侧栏能带确认的一键发放、员工详情页底部按钮不再用「返回列表 · 接受任务」这种迷惑文案。

总览：四个问题 → 四个效果

# 现网问题 要做什么 达成效果（用户侧）
Bug 1 钉钉机器人发的任务链接跳到外部浏览器，免登失效 通知卡片 URL 包一层钉钉 applink；链接带上 fromView=new 点「打开任务详情」在钉钉内打开工作台，自动登录
Bug 2 工作台登录页仍像测试登录页，文案矛盾 生产环境隐藏测试表单；统一用户向文案；更新根路径说明 打开 /workbench 看到正式产品页：「正在连接钉钉…」
Bug 3 主管聊天右侧草案区没有发放入口，只能打字说「发放」 侧栏仅「发放任务」一个按钮；两步确认都用 popup，走 agent prepare → 确认 → publish 点按钮 → 弹窗预检 → 聊天看预览 → 再弹窗确认 → 任务下发；侧栏不会冒出第二个按钮
Bug 4 员工改派详情页蓝按钮写「返回列表 · 接受任务」，其实不会接受，还常跳错 Tab 详情页保持只读；按钮改为清晰的「前往待承接」导航 用户明白：详情只看背景，接受要在「待承接」列表点「接受」

Bug 1 员工通知链接 · 钉钉内打开

改之前
  • 通知里是裸 HTTPS 链接，如 https://域名/workbench/employee/task?taskNo=TK-001
  • 钉钉可能用系统浏览器打开 → 没有 JSAPI → 无法免登
  • 只有主管 chat 深链做了 applink 包装，员工通知没有
改之后
  • 链接经 applink.dingtalk.com/page/link?url=… 包装
  • 在钉钉客户端内打开微应用 webview
  • URL 带 fromView=new，与「新任务 / 待承接」一致

改动位置

src/integrations/dingtalk/workbench-notify.ts · 复用 src/view/workbench-chat-link.ts 的 wrapUrlForDingtalkClient

任务发布、改派、停止、催办提醒、待办、进展推送等所有发给员工的 ActionCard / 机器人 1:1 链接。

Bug 3 草案侧栏 · 一键发放（带确认）

为什么走 agent 发消息，而不是直接调发布 API？

  • 沿用现网 prepare → 用户确认 → publish 两回合，latestDraft / 暂存状态与聊天一致
  • 对话里留下预览表和确认记录，可审计、可回溯
  • 不旁路 orchestrator 门禁（未指派、缺标题等仍由工具软返回）

交互流程（主管在「智能规划助手」右侧草案面板）

  1. 点击侧栏 「发放任务」（有草案时出现；未指派 > 0 时 modal 内警告）
  2. 第一步确认框 → 自动向 agent 发送：「请对当前草案做发放预检并展示预览」
  3. 聊天区出现发放预览表（与口头说「可以发放了」效果相同）
  4. 侧栏出现 「确认发放」 → 再弹确认 → 发送：「确认发放」
  5. 任务写入 SQLite，员工收到通知（Bug 1 修复后链接在钉钉内可开）
[草案侧栏] [聊天区] 子任务 5 · 未指派 0 （用户此前规划对话…） [编辑草案表格] [发放任务] ← 新增 │ ▼ 第一步 modal 「将发起发放预检并在对话中展示预览」 [取消] [继续] │ ▼ agent: prepare_publish_task …… 助手：预览表 + 发放说明 │ ▼ 第二步 [确认发放] ← 侧栏出现 （用户可见完整预览） │ ▼ 发送「确认发放」 agent: publish_task 助手：已发放 TK-xxx

侧栏按钮示意

本会话草案
子任务 5 · 未指派 0
编辑草案表格 发放任务
预览出现后 ↓
确认发放

改动位置

src/web/manager-workbench-pages.ts · 复用现有 POST /api/workbench/conversation/send，不新增发布 API。

Bug 4 员工详情页底部 · 去掉迷惑按钮

你已确认方案：详情页保持只读，接受/拒绝仍在「待承接」列表卡片上操作。

改之前（迷惑）
返回列表继续操作 返回列表 · 接受任务
  • 蓝色主按钮看起来像「一点就接受」
  • 实际只是跳回列表，且常落到「进行中」Tab
  • ASSIGNED 任务的「接受」在「待承接」里，用户找不到
改之后（清晰）
返回列表继续操作 前往待承接
  • 主按钮只做导航，文案不再假装「接受任务」
  • ASSIGNED → 固定跳 view=new（待承接）
  • 进行中类 → 跳 view=current
  • 配合 Bug 1：通知链接也带 fromView=new
页面说明（保留）
「接受、拒绝、进度等操作请在『待承接 / 进行中』列表卡片上完成；本页查看完整背景与分工。」

改动位置

src/web/assignment-workbench.ts — 员工详情页 footer 文案与 listHref 逻辑

改完后的整体体验

员工 钉钉点通知 → 应用内打开 → 看详情 → 「前往待承接」→ 列表点「接受」
主管 聊天规划 → 右侧看草案摘要 → 「发放任务」→ 预览 → 「确认发放」
登录 钉钉内打开工作台 → 正式加载页 → 自动跳转主管/员工首页
运维 无需新 env；确认 ASSIGNMENT_WEB_PUBLIC_BASE_URL 与微应用首页一致即可

验证方式（开发自测）

  • npm test — 尤其 workbench-notify.test.ts（applink + fromView=new）
  • npm run build:workbench-login 后打开 /workbench（生产 env）看文案
  • 主管 chat：有 draft → 侧栏发放两步骤 → 对话有预览 → 确认后任务入库
  • 员工：mock 通知 URL 进详情 → 底部「前往待承接」→ view=new 且有「接受」按钮

不在本次范围

  • 详情页内联「接受任务」按钮（你选了保持列表操作）
  • 直接绕过 agent 的新发布 REST API
  • 数据库 schema 变更
