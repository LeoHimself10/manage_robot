## 1. 背景

质量侧对接后，当前产品目标从“完整任务闭环”收敛为先做一个可演示、可评估的任务拆解 Demo。Demo 重点验证 Agent 能否根据质量/研发任务背景完成输入质检、分类、WBS 拆解、任务包生成和派发门禁校验。质量后续会提供真实业务场景、分类口径和具体实例，用于优化 Agent 的分类与拆解效果。

本设计只覆盖 Demo/MVP，不包含 OA 自动流转、承接三态、电子签名、执行中延期/换人、节点反馈与验收闭环。这些能力作为后续版本演进。

## 2. 目标与非目标

### 2.1 目标

- 主管输入质量或研发任务背景后，Agent 先检查信息是否足够，不足则追问。
- 由 **大模型**输出场景分类与 WBS / 结构化任务包（提示词可引用领域口径；**非**代码内关键词分类或固定骨架模板）。
- Agent 对任务包执行派发门禁校验，确保交付物、完成标准、时间节点、反馈频率齐全。
- Agent 输出可复制到钉钉或文档中的 Markdown/表格结果。
- 对质量相关任务，Agent 输出是否建议开启 CAPA 的建议字段、理由和免责声明。

### 2.2 非目标

- 不自动创建钉钉 OA 审批流程。
- 不处理员工认领、拒绝、延期、无法完成或换人审批。
- 不接入电子签名。
- 不做执行中的节点反馈、验收和复盘。
- 不把 CAPA 建议作为正式质量体系判断，最终仍以质量授权人员和 QMS 流程为准。
- 不依赖 HR 简历自动分配任务；若展示人员建议，必须标注能力信息可能过时。

## 3. 推荐方案

采用“流水线 + 轻状态”的设计，而不是一次性让模型输出所有内容。

流程为：

```text
基础输入护栏 -> Qwen 结构化生成（信息充分性 + 分类 + 任务包 + 质量域 CAPA + 门禁自检）-> 结构校验与派发门禁二次确认 -> Markdown 输出；失败 -> GENERATION_FAILED
```

质量提供真实案例后，可分别评估模型输出的分类、CAPA、任务包结构与门禁结果；规则侧不参与「无模型时的兜底生成」。

## 4. 核心流程

### 4.1 输入质检

Agent 首先由 Qwen 判断主管输入是否足以拆解任务；代码侧除空输入等基础护栏外，若超过 **`INPUT_MAX_CHARS`**（可配置）则 **不调用模型**、直接提示用户缩短或分段，避免异常长文本消耗配额且违背「信息不足不硬拆」的心智。不用关键词正则替代 **语义** 充分性判断。质量类任务重点要求模型检查：

- 问题来源。
- 产品、批次、版本或使用场景。
- 问题现象。
- 影响范围。
- 当前是否已有证据。
- 是否存在客户、生产、出货、安全或法规影响。
- 期望完成时间或关键时间约束。

信息不足时，模型输出低置信度、缺失信息与追问清单，Agent 返回 `NEEDS_MORE_INFO`，不生成 WBS。

### 4.2 场景分类

Demo 先支持小集合分类：

- 质量：生产/过程异常、检验/测试异常、客诉/售后、供应商问题、设计相关质量任务、其他/不确定。
- 研发：需求/设计输入落地、方案开发与论证、验证与确认任务、设计变更行动项、其他/不确定。

分类输出需包含：

- 分类结果。
- 置信度或判断依据。
- 若不确定，列出需要补充的信息。

### 4.3 CAPA 建议

CAPA 字段为纯建议，不具备正式质量体系效力。输出结构：

```text
capa_advisory: NOT_REQUIRED | RECOMMENDED | UNCERTAIN | INSUFFICIENT_INFO
capa_rationale: 建议理由列表
capa_disclaimer: “该建议仅用于任务拆解与质量沟通参考，最终是否开启 CAPA 以质量授权人员和公司 QMS 流程判定为准。”
capa_prompting_questions: 当信息不足或不确定时，列出需要质量补充的问题
```

Demo 阶段不固化 CAPA 判定规则，只要求质量域模型输出 `capaAdvisory`，并由 Schema 校验保障字段存在；最终建议质量仍由授权人员判断。待质量提供真实样本后，优先优化提示词、Schema 与门禁口径，而不是恢复无模型规则稿。

### 4.4 提示词口径与 WBS

Qwen 根据输入背景与域提示直接生成任务包；提示词可引导质量类任务参考以下处理口径：

- 问题事实确认。
- 临时遏制或影响控制。
- 根因分析。
- 纠正措施建议。
- 效果验证或关闭准备。

上述任务不是所有场景都强制出现，Agent 需要在分类依据、任务目标或开放问题中体现为什么保留或不保留。

### 4.5 派发门禁

Demo 阶段保留派发门禁，但不真正派发。门禁校验每个子任务是否包含：

- 交付物。
- 完成标准。
- 时间节点。
- 反馈频率。

Qwen 需输出 `gateSelfCheck`；代码仍按同一四必填口径做二次硬校验。若缺失，则输出“门禁未通过”和缺失项清单，不输出“可派发最终稿”。归一化层不得把缺失项补成默认文案或默认时间。

## 5. 输出形态

Demo 输出以 Markdown 为主，方便复制到钉钉、文档或评审材料中。建议包含：

1. 任务理解摘要。
2. 场景分类与依据。
3. CAPA 建议、理由和免责声明。
4. WBS 总览。
5. 子任务包表格。
6. 派发门禁结果。
7. 仍需主管/质量确认的问题。

## 6. 后续演进

Demo 验证拆解效果后，再考虑以下能力：

- 员工执行中申请延期、无法完成或变更任务，提交主管审核并可委托新承接人。
- 钉钉 OA 审批自动创建与状态同步。
- 承接/拒绝时接入电子签名，并同步到 OA 留存。
- 外部 Agent Web 链接，用于复杂表格编辑与跨钉钉/飞书复用。
- HR 能力清单增强：从简历升级为结构化、带更新时间与任务表现反馈的能力画像。

## 7. 测试与评估

Demo 评估以真实样本为主。质量后续提供案例后，至少形成 10 条黄金样本，用于评估：

- 分类是否合理。
- CAPA 建议是否符合质量人员预期。
- WBS 是否覆盖关键处理步骤。
- 任务包交付物与完成标准是否清晰。
- 门禁是否能发现缺失字段。

## 8. 风险与缓解

- HR 简历可能过时：Demo 不把 HR 推荐作为核心能力；后续若展示推荐，必须显示来源与更新时间。
- CAPA 建议被误解为正式结论：所有输出必须包含免责声明，并在 PRD 中标注最终以 QMS 和授权人判定为准。
- 模型分类不稳定：用真实样本建立回归集，逐步优化提示词、输出 Schema 与门禁口径。
- Demo 范围膨胀：OA、电子签、承接闭环和外部 Web Agent 都不进入当前 MVP。

## 9. 本地 Demo 运行方式

实现完成后，可用以下命令运行：

```bash
npm install
npm test
npm run typecheck
npm run demo
npm run demo:scenarios
```

`npm run demo` 会输出一份 Markdown 任务拆解草案，包含输入理解、分类、CAPA 建议、WBS 任务包、派发门禁和仍需确认的问题。`npm run demo:scenarios` 在多套固定背景上端到端冒烟（需有效 `QWEN_API_KEY`），用于联通性与回归观察。
