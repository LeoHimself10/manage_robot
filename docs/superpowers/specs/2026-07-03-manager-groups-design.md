# 主管组管理设计

**日期**：2026-07-03  
**状态**：设计已初步确认，待实现  
**适用实例**：优先用于 `mingsibot`；微光实例默认保持现状

## 1. 背景

明思侧准备让多个业务团队使用任务工作台。现有系统把主管权限绑定到单个自然人：谁发布任务，谁才能在主管工作台看、改派、催办、停用和管理项目。这个模型不适合“几个人共同承担一个主管角色”的场景。

新的产品表达是：**管理员在前台维护多个主管组；组内成员完全同权；组间隔离；普通主管最多属于一个主管组。**

## 2. 目标

- Admin 可在工作台前台创建、编辑、停用主管组。
- Admin 可把通讯录人员加入或移出主管组。
- 普通主管最多属于一个主管组，前端和后端都要阻止重复加入。
- 组内成员完全同权，可共同管理该组名下的任务、项目、看板和正式任务操作。
- 不同主管组之间互相不可见。
- 真实操作者必须保留审计：发布、改派、催办、停用、调整项目归属都记录自然人。
- 功能可按实例开启，先服务 `mingsibot`，不影响微光现网。

## 3. 非目标

- 第一版不允许普通主管同时属于多个主管组。
- 第一版不做跨组协作或临时授权。
- 第一版不共享未发布的个人聊天草案，避免多人同时编辑同一份草案产生覆盖。
- 第一版不把多个用户伪装成同一个 `userId`。
- 第一版不改变员工端身份模型，员工仍按自己的子任务查看和反馈。

## 4. 权限模型

| 身份 | 能力 |
|------|------|
| Admin | 管理所有主管组、成员、状态；可查看全局；不受单组归属限制 |
| 组内主管 | 对本组正式任务、项目、Dashboard、催办、改派、停用等完全同权 |
| 组外主管 | 看不到其他组的任务、项目和看板 |
| 未入组主管 | 保持现有个人主管模式，或由实例策略限制其发布入口 |
| 员工 | 只看分配给自己的子任务，不因主管组改变扩大权限 |

“完全同权”仅指已发布的正式工作对象。个人聊天主线程和未发布草案仍属于发起人个人；发布成功后任务归属到主管组。

## 5. Admin 前台入口

在 Admin 工作台「权限中心」新增「主管组」区域。

Admin 可以：

- 查看主管组列表：组名、状态、成员数、任务数、项目数。
- 新建主管组：填写组名、说明、启用状态。
- 编辑主管组：改名、说明、启用/停用。
- 添加成员：通过现有通讯录搜索选择人员。
- 移除成员：从组中移除，不删除历史审计。
- 查看成员归属冲突：若人员已属于其他主管组，提示先从原组移除。
- 迁入历史任务/项目：选择某个成员，将其既有个人任务和项目迁入当前主管组，迁入前显示数量预览。

停用主管组后，普通成员不能再用该组范围发新任务或做管理操作；Admin 仍可查看和恢复。

## 6. 数据归属

新增主管组概念后，正式对象同时保留“归属组”和“真实人”。

建议字段：

- `manager_groups`：主管组主表。
- `manager_group_members`：成员表，`user_id` 唯一约束保证普通主管单组归属。
- `tasks.manager_group_id`：正式任务归属组，可为空以兼容旧个人任务。
- `projects.manager_group_id`：项目归属组，可为空以兼容旧个人项目。
- 现有 `tasks.manager_user_id` 继续保留，表示原始发布主管或责任主管。
- 任务事件继续记录 `actor_user_id`，表示真实操作者。

兼容规则：

- 有 `manager_group_id` 的任务按组授权。
- 没有 `manager_group_id` 的任务沿用现有个人主管授权。
- Admin 可显式把历史个人任务/项目迁入某个主管组。

## 7. 使用流程

1. Admin 打开「权限中心」里的「主管组」。
2. 创建「明思项目主管组」和「商务部主管组」。
3. 分别添加成员；同一普通主管不能被加入两个组。
4. 主管登录后，系统自动解析其唯一主管组，不需要选择。
5. 主管发布任务时，正式任务写入该主管组；真实发布人仍记录当前用户。
6. 任一组内成员打开任务列表、项目总览、周度 Dashboard 或 Agent 查询时，看到本组范围。
7. 任一组内成员对本组任务改派、催办、停用、调整项目归属时，权限通过，审计记录该操作者。
8. 组外主管访问任务详情或接口时返回无权限。

## 8. 影响范围

需要统一改为“主管组范围”的入口：

- 主管任务列表和任务详情。
- 项目列表、项目详情、项目归属调整。
- 主管周度 Dashboard。
- 绩效看板中主管视角的数据范围。
- Agent 工具：查询任务、查看详情、改派、催办、发布、项目工具。
- 工作台按钮权限：组内成员可操作，组外成员不可操作。
- 员工反馈后的主管通知。

通知建议第一版采用“通知本组成员”的策略，消息中标明真实触发人和原任务发布人。若后续反馈太吵，再加组级通知策略。

## 9. Agent 口径

主管组开启后，主管工具语义从“我名下任务”变成“我所在主管组的任务”。

Prompt 和工具描述需要避免误导：

- `list_managed_tasks`：列出当前主管可管理范围内的正式任务。
- `get_task_detail`：组内主管可查看本组任务详情。
- `reassign_task` / `send_subtask_reminder`：组内主管可操作本组任务。
- 发布任务时，系统注入当前主管组，模型不需要猜组。

Admin 工具仍保留全局视角。

## 10. 实例开关

建议新增实例开关：

```env
WORKBENCH_MANAGER_GROUPS_ENABLED=1
```

默认关闭。`mingsibot` 开启后使用主管组模式；微光实例默认继续按个人主管模式运行。

## 11. 迁移策略

- 数据库只做向前兼容新增表和字段，不破坏旧数据。
- 已有个人任务默认不自动迁入，避免误共享历史数据。
- Admin 前台提供显式迁入动作：选择主管组和成员，预览该成员个人任务/项目数量，再确认迁入。
- 迁入后任务归属组，原 `manager_user_id` 保持不变，用于显示“原发布主管”。
- 回滚时关闭实例开关，旧个人权限仍可兜底；已迁入任务需要 Admin 决策是否保留组字段。

## 12. 验收标准

- Admin 能在前台创建两个主管组，并分别添加成员。
- 同一普通主管不能同时加入两个主管组。
- 明思项目主管组成员能互相看到并操作本组任务和项目。
- 商务部主管组成员看不到明思项目主管组任务。
- 组内成员操作他人发布的任务时，审计记录真实操作者。
- 未发布草案不共享；发布后的正式任务进入主管组范围。
- 微光实例未开启开关时，原个人主管权限行为不变。
- 相关 API 的越权访问返回 403 或等价无权限结果。

## 13. 测试建议

- 存储层：主管组成员唯一性、任务组范围查询、历史任务迁入。
- Web API：列表、详情、改派、催办、停用、项目归属的组内成功和组外失败。
- Admin UI：新建组、加人、移除、重复成员提示、停用组。
- Agent 工具：组内查询和操作成功；组外任务不可见。
- 回归：未开启 `WORKBENCH_MANAGER_GROUPS_ENABLED` 时现有主管工作台测试保持通过。
