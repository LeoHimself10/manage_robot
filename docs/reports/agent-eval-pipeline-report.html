Agent 评估管道
与上线用量统计

面向非技术同事的说明：我们解决了什么问题、现在能看什么、日常该怎么用。

以前评估脚本多且重复，发版前同一能力测好几遍；上线后也看不清谁在用、Token 花多少、质量好不好。
现在变成五层清晰流程 + 统一成绩单 + Admin 运营看板 + 线上质量记录，发版更省 API，运营有数可看。

1评估体系：从 18 个脚本到 5 个入口

记住下面五层即可，不必再记十几个 eval 命令。

以前
  • 18 个 eval 命令，很多测同一件事
  • 发版一次评估重复跑 2～3 遍
  • 约 60+ 轮大模型对话，耗时长、耗 API
  • 报告格式不统一，难对比历史
现在
  • 5 个主入口：unit → integration → spot → chains → release
  • 发版编排不重复跑同一套
  • 约 45 轮，节省约 25% API
  • 统一 eval-summary.json + 历史记录
层级 命令 做什么 要 API Key 时长
L0eval:unit自动化检查，不调大模型否~2 分钟
L1eval:integration会议待办等 mock 全链路否~3 分钟
L2eval:spot单轮专项（点将、Portfolio 等）是~15 分钟
L3eval:chains多轮真实话术（28+ 轮）是~25 分钟
L4eval:release发版 / nightly 唯一编排是~35 分钟

发版硬门槛（不过关 = 发版 eval 失败）

L0 全过 · 非 Portfolio 回归全过 · 6 条核心多轮链（28 轮）全过

5线上质量评分（不挡用户）

后台规则检查；约 5% 随机抽样，异常事件 100% 记录。不会因评分让用户多等或撤回回复。

会记录
  • 话术是否泄露内部工具名
  • 是否误发布
  • 是否超轮次
告警 SLO（可配置）
  • 超轮次比例 < 2%/天
  • 误发布 = 0
  • p90 响应 < 120 秒

6失败案例 → 测试用例（闭环）

线上发现质量问题 → 待处理队列 → 一键生成测试骨架 → 纳入发版 eval，防止再犯。

线上评分失败 → 待处理队列 → 晋升 fixture → 下次发版自动测

7您日常怎么用

  1. 改 Prompt / 工具后本地试跑 eval:spot 或 eval:chains
  2. 合并 PR 前看 CI 是否跑过 eval:unit（或本地跑一遍）
  3. 发版前 / 每周跑 eval:release（需要 QWEN_API_KEY）
  4. 看运营数据浏览器打开 Admin → 运营看板；或跑用量周报脚本
  5. 对比两次发版eval:compare 看哪一 stage 变差
