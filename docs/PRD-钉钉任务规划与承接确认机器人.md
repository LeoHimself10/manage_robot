## 1. 概述

### 1.1 背景

公司业务中研发与质量活动强依赖**可追溯的责任分工、清晰的交付定义与节点反馈**。当前常见问题集中在主管下发任务时**拆解粗、交付物与验收口径不清、范围边界模糊、依赖与责任人不明**，执行层只能靠反复沟通猜测意图，带来返工、延期与合规记录口径不一致风险。

组织层面希望先通过 Demo 验证 Agent 对质量/研发任务的**输入质检、分类、WBS 拆解、任务包生成与派发门禁**能力；待质量提供真实业务场景和分类样本后，再迭代分类效果，并逐步扩展到承接确认、节点反馈、OA 同步等完整闭环。

### 1.2 产品一句话定义

帮助主管在派发前把「目标」转化为**可审阅、可门禁校验、可复制到钉钉或文档中继续协作**的结构化任务拆解草案；MVP 先以 **Qwen 云 API** 为核心推理引擎验证拆解质量，不做正式派发、承接确认和 OA 流转。

### 1.3 产品定位与边界


| 维度       | 说明                                                |
| -------- | ------------------------------------------------- |
| **是什么**  | Demo/MVP 阶段是任务拆解与门禁校验工具：**信息充分性判断、场景分类与 WBS 由 Qwen 生成**；确定性规则仅做空输入护栏、结构化校验与派发门禁二次确认 |
| **不是什么** | MVP 不做 OA 自动流程、承接三态、电子签名、执行中变更、节点反馈与验收闭环          |
| **合规声明** | CAPA 字段仅为**建议**，最终是否开启 CAPA 以质量授权人员和公司 QMS 流程判定为准 |
| **模型策略** | MVP 默认接入 Qwen 云 API（首选）；当前不做自动决策闭环，仅提供可审阅建议       |
| **工程补强（v1.3.1 文档）** | 实现可对过长输入先做护栏、对大段 Markdown 可做有限 PII 脱敏、会话内带摘要以降低重复描述；均为 **工程与合规辅助**，不视为新增「产品能力」或扩大 FR 范围（仍不做 OA/承接三态等） |

## 2. 目标与成功标准

### 2.1 业务目标

1. 验证 Agent 是否能把质量/研发任务背景拆成清晰的 WBS 与任务包。
2. 验证模型是否能在信息不足时主动反问，阻止直接生成空洞计划。
3. 验证派发门禁是否能发现交付物、完成标准、时间节点、反馈频率缺失。
4. 对质量任务输出「是否建议开启 CAPA」的参考建议，辅助质量人员判断。

### 2.2 成功指标（建议首期观测）


| 指标         | 说明                                 |
| ---------- | ---------------------------------- |
| 分类合理率      | 质量/研发人员认为场景分类合理的比例                 |
| 拆解可用率      | 主管认为 WBS 草案可作为任务计划基础的比例            |
| 门禁发现率      | 能否识别交付物、完成标准、时间节点、反馈频率缺失           |
| CAPA 建议接受度 | 质量人员认为 CAPA 建议方向合理的比例              |
| 追问有效性      | 输入不足时，追问问题是否能帮助补齐关键上下文             |
| 结构化输出合规率   | 模型输出可被系统解析为标准任务包结构（JSON/Schema）的比例 |
| 平均响应时延 P95 | 从发起生成到返回拆解稿的 P95 耗时                |
| 单次生成成本     | 单次任务拆解的平均 Token 成本与波动区间            |


> 说明：Demo 评估以真实样本和业务专家人工评审为主，不用于人员绩效评价。

### 2.3 非目标（V1 明确不做）

- 自动关闭 CAPA、自动裁定责任方。  
- 自动创建或同步钉钉 OA 审批流程。  
- 员工认领/拒绝、延期/无法完成、换人审批、电子签名。  
- 执行中节点反馈、验收与任务定义复盘闭环。  
- 替代现有缺陷/CAPA/项目管理系统。

## 3. 用户与场景

### 3.1 角色


| 角色    | 主要职责                             |
| ----- | -------------------------------- |
| 任务发起人 | 多为质量/研发主管或项目经理；录入背景、审阅 AI 任务拆解草案 |
| 质量评审人 | 评估场景分类、CAPA 建议和质量任务拆解是否合理        |
| 协作人   | 提供输入、评审或支持；MVP 中仅作为任务包字段展示       |
| 承接人   | 后续版本执行子任务、承接确认与节点反馈；MVP 不进入承接流程  |
| 系统管理员 | 模板、权限、提醒策略配置（可与 IT 兼任）           |


### 3.2 首期覆盖场景（质量 + 研发）

#### 3.2.1 质量域（示例）


| 子类型（示例）  | 典型来源              | 拆解侧重点            |
| -------- | ----------------- | ---------------- |
| 生产/过程异常  | 产线、测试工位           | 遏制、批次范围、工艺/工序接口  |
| 检验/测试异常  | IQC/IPQC/OQC、研发测试 | 复测范围、方法、样本、失效模式  |
| 客诉/售后    | 客户现场、退回品          | 影响评估、复现条件、临时沟通策略 |
| 供应商问题    | 来料、制程审核           | 供应商调查、隔离、纠正措施接口  |
| 设计相关质量任务 | 设计缺陷线索            | 与设计变更、验证、风险更新衔接  |


底层拆解骨架建议对齐 **8D/CAPA 思路**（事实确认 → 遏制 → 根因 → 纠正 → 验证关闭），**但不等同于**公司正式 CAPA 表单；正式记录流程遵循现有质量体系。

质量域输出需包含 CAPA 建议字段。该字段只用于提示是否建议质量人员进一步评估 CAPA，不自动创建 CAPA，不替代质量授权人员判断。

#### 3.2.2 研发域（示例）


| 子类型（示例）   | 典型触发      | 拆解侧重点           |
| --------- | --------- | --------------- |
| 需求/设计输入落地 | 评审遗留项     | 需求条目、假设、约束、验收口径 |
| 方案开发与论证   | 系统/软硬件/结构 | 备选方案、风险、验证策略接口  |
| 验证与确认任务   | V&V 计划缺口  | 追溯需求/风险、方法、通过准则 |
| 设计变更行动项   | ECN/变更评审  | 影响范围、回归验证、文档更新  |


研发类任务强调 **范围边界（in-scope / out-of-scope）** 及与**需求/风险**的追溯字段（若公司有编号体系则关联；若无则 V1 可为可选）。

## 4. 核心概念：任务包（Task Package）

每个子任务以统一结构描述，避免「只有标题和截止日期」。

### 4.1 字段定义（最小必填）


| 字段       | 质量域    | 研发域    | 说明                      |
| -------- | ------ | ------ | ----------------------- |
| 子任务名称    | 必填     | 必填     | 一句话说明做什么                |
| 任务目标     | 必填     | 必填     | 与上一级目标的承接关系             |
| 范围边界     | 建议     | **必填** | 做什么 / 不做什么              |
| 推荐负责人    | 必填     | 必填     | 可由 HR 能力清单推荐，发起人可改      |
| 协作人      | 选填     | 选填     | 需提供输入或评审的角色             |
| 输入材料     | 必填     | 必填     | 开工前必须具备的资料/样品/权限        |
| 执行动作     | 必填     | 必填     | 阶段级或步骤级                 |
| **交付物**  | **必填** | **必填** | 可列举的具体产出                |
| **完成标准** | **必填** | **必填** | 可验证的通过条件                |
| **时间节点** | **必填** | **必填** | 开始、检查点、截止               |
| **反馈频率** | **必填** | **必填** | 如每日/隔日/节点               |
| 建议验收人    | 建议     | 建议     | 后续派发时由谁判定完成；MVP 仅作为拆解字段 |
| 风险与待确认项  | 建议     | 建议     | 卡点、需决策点                 |
| 追溯信息     | 选填     | 建议     | 需求 ID、风险项、适用标准条目等       |


### 4.2 CAPA 建议字段（质量域）

质量相关任务输出时，Agent 需增加以下顶层字段：


| 字段                         | 取值/说明                                                              |
| -------------------------- | ------------------------------------------------------------------ |
| `capa_advisory`            | `NOT_REQUIRED` / `RECOMMENDED` / `UNCERTAIN` / `INSUFFICIENT_INFO` |
| `capa_rationale`           | 建议理由列表，说明为何建议或不建议进一步评估 CAPA                                        |
| `capa_disclaimer`          | 固定免责声明：该建议仅用于任务拆解与质量沟通参考，最终是否开启 CAPA 以质量授权人员和公司 QMS 流程判定为准         |
| `capa_prompting_questions` | 当信息不足或不确定时，需要质量补充的问题                                               |


### 4.3 派发门禁（质量与研发一致）

在输出最终拆解稿前，系统校验：若缺少 **交付物、完成标准、时间节点、反馈频率** 四项之一，则输出「门禁未通过」和缺失项清单，不标记为可派发稿。

## 5. 端到端流程（业务视角）

```text
发起 → 基础输入护栏 → 模型策略选择（Qwen+参数）→ Qwen 结构化输出（信息充分性、追问、分类、WBS、质量域含 CAPA、门禁自检）
→ 结构化校验与派发门禁二次确认 → 成功则输出 Markdown；失败则 GENERATION_FAILED（不重生成规则稿）
→ 发起人审阅与修订 → 输出可复制的钉钉/文档拆解稿 → 业务评审 Demo 效果
```

### 5.1 MVP 输出

MVP 不自动派发任务，仅输出可用于业务评审和人工继续协作的拆解稿。输出应包含：

- 任务理解摘要。
- 场景分类与依据。
- CAPA 建议、理由和免责声明（质量域）。
- WBS 总览。
- 子任务包表格。
- 派发门禁结果。
- 仍需主管/质量确认的问题。

### 5.2 本地 Demo 运行方式

研发实现完成后，可通过 `npm run demo` 生成一份示例 Markdown 拆解稿（须配置 `QWEN_API_KEY`，可用本地 `.env`，勿提交仓库）。该命令仅用于本地演示，不代表钉钉机器人或 OA 流程已经接入。

### 5.3 后续版本：承接确认与执行反馈

承接三态、延期/无法完成申请、换人审批、节点反馈、验收与复盘进入后续版本；其中员工在任务执行过程中提出延期或无法完成时，应提交主管审核，并允许主管委托新的承接人。

### 5.4 Qwen 接入后的推理链路（MVP）

1. **预处理层（确定性约束）**：只做空输入等基础护栏、**`INPUT_MAX_CHARS` 超长护栏（不静默截断）**与上下文拼接；非空输入交给模型判断语义充分性。
2. **策略层（可配置）**：按域提示选择系统提示词、Qwen 型号与参数。
3. **生成层（Qwen 云 API）**：结构化 JSON 输出（**`responseIntent`/`assistantMessage`**、信息充分性、分类、任务包、追问列表、`gateSelfCheck`；**质量域须含 CAPA 建议对象**，研发域不含）。HTTP 层可 **SSE 流式接收**后拼成整段再解析，语义上仍为 **单次结构化结果**。
4. **校验层（确定性规则）**：基于字段 Schema、域内 CAPA 规则与派发门禁二次确认；归一化层不得为核心业务字段填充语义默认值；不通过则 **`GENERATION_FAILED`** 或输出门禁未通过草案，**不使用关键词分类或模板 WBS 替代模型输出**。
5. **可选重试**：可在产品层配置「同请求有限次重试」；当前实现以显式失败与人工介入为主。
6. **输出层（人审优先）**：校验通过后输出 Markdown/表格拆解稿，并附带 trace（请求 ID、模型、Token、时延等）。

> 原则：MVP 阶段「**模型负责生成草案**，**规则负责约束与门禁**，**人负责最终确认**」；规则不作为无模型时的替代生成路径。

### 5.5 钉钉 Stream 机器人（工程试点）

与 PRD 产品边界对齐的 **试点部署**：企业通过 **钉钉 Stream** 收文本、`createTaskPlanningDemo` 出稿。单次用户触发 **原则上一条 Markdown 终稿**（闲聊 / 追问 / 讨论 / 成功草案 / 失败说明）；**主文案**来自模型 **`assistantMessage`**，结构化追问可来自 **`openQuestions`**，**不由代码拼接固定引导标题或 Markdown 列表符号前缀**。服务端 Qwen **`QWEN_STREAM` 默认开**；钉钉不向用户推送「处理中」或流式进度气泡（详见 **`docs/deploy-aliyun-dingtalk.md`**、**`docs/Qwen-接入实施说明.md`**）。一键更新容器：`scripts/ecs-deploy-dingtalk.ps1`。

| FR-04 | 任务包校验       | 派发门禁：四必填字段                                     | P0  |

## 9. 与质量 / 研发体系的协作约定

### 9.1 质量部关注点

- 任务骨架对齐现有 **NCR/CAPA/8D** 口语习惯即可，**正式编号与关闭权限仍在 QMS**。  
- 「遏制、根因、纠正、验证」类子任务建议通过提示词与评测样本引导模型在合适场景中输出，可由质量代表评审提示词口径与样本输出。
- 证据反馈字段与现场记录习惯对齐（照片、批次、检验记录编号等）。
- CAPA 字段只输出建议：`NOT_REQUIRED` / `RECOMMENDED` / `UNCERTAIN` / `INSUFFICIENT_INFO`；最终是否开启 CAPA 仍由质量授权人员和 QMS 流程判定。

### 9.2 研发部关注点

- 研发模板默认带 **范围边界**；若有 **需求/风险** 编号规范，在 FR 中升级为「建议必填」。  
- 方案/验证类任务默认追问：**验证对象、方法、样本、通过准则**。  
- 与设计评审、变更流程的接口：V1 **弱关联**（链接或 ID）；深度集成放到后续版本。

## 11. 风险与缓解


| 风险         | 缓解措施                                       |
| ---------- | ------------------------------------------ |
| 表单负担过重     | 短模板、支持语音/粘贴纪要自动抽取字段（后续）；强调减少返工收益           |
| AI 输出不可靠   | 模板约束 + 发起人必审 + 质量/研发评审人可退回修改               |
| HR 数据滞后    | Demo 不把 HR 推荐作为核心能力；后续展示能力清单更新日期，并允许主管覆盖推荐 |
| CAPA 建议被误解 | 固定免责声明；输出为建议字段，不自动创建 CAPA，不替代 QMS          |
| 与现有流程两张皮   | 制度上明确：本机器人为协作层，正式记录仍走 QMS                  |
| 模型成本失控     | 设置单次调用上限、超限告警、按场景选择轻量/标准模型                 |
| 第三方模型波动    | 建立回归集与上线前基线评测；失败路径告警与人工补录/重试流程明确               |
| 供应商绑定风险    | 抽象模型调用接口与策略层，后续可切换私有化或多模型                  |

## 12. 待决策事项（需质量 / 研发 / 管理层确认）

1. **质量子类型优先级**：Demo 首期上线哪几类（如仅「生产异常 + 测试异常」）？
