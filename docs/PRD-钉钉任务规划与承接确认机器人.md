## 1. 概述

### 1.1 背景

公司业务中研发与质量活动强依赖**可追溯的责任分工、清晰的交付定义与节点反馈**。当前常见问题集中在主管下发任务时**拆解粗、交付物与验收口径不清、范围边界模糊、依赖与责任人不明**，执行层只能靠反复沟通猜测意图，带来返工、延期与合规记录口径不一致风险。

组织层面希望将「口头/模糊安排」升级为**结构化任务包 + 强制承接确认 + 节点化证据反馈**，并在**钉钉**内落地为机器人，便于触达与协作。

### 1.2 产品一句话定义

帮助主管在派发前把「目标」转化为**可承接、可验收、可复盘**的结构化任务计划；承接人必须**确认承接 / 提出修改 / 无法承接并说明理由**；执行过程按节点回收**进展、证据与阻塞**，降低无效劳动与沟通成本。

### 1.3 产品定位与边界


| 维度       | 说明                                              |
| -------- | ----------------------------------------------- |
| **是什么**  | 管理闭环类工具（兼信息整合）：任务定义质量提升、承接确认、节点反馈               |
| **不是什么** | 不替代 QMS/PLM；不自动判定质量责任；不自动生成需正式签批归档的 CAPA/DHF 终稿 |
| **合规声明** | V1 产出视为**内部协作草稿**，正式质量体系记录仍由授权岗位审核落档            |

## 2. 目标与成功标准

### 2.1 业务目标

1. 降低因「任务定义不清」导致的返工与重复解释。
2. 提升承接人对目标、交付物、完成标准、时间的**首次理解一致率**。
3. 减少「承接沉默」：未确认、不反馈的状态可被发现与升级。
4. 为后续复盘提供结构化数据（延期原因分布、阻塞类型等）。

### 2.2 成功指标（建议首期观测）


| 指标      | 说明                        |
| ------- | ------------------------- |
| 承接确认率   | 派发后在约定时限内完成「确认/修改/拒接」的比例  |
| 一次理解通过率 | 承接人无需修改即可确认承接的比例          |
| 节点反馈率   | 到达检查节点时，按模板提交反馈的比例        |
| 交付物完整率  | 验收时交付物与「完成标准」一致的比例        |
| 延期原因分布  | 「目标不清、输入缺失、协作不明」类原因占比是否下降 |


> 说明：首期不建议将指标直接与个人绩效强绑定，以降低抵触；以流程改进为主。

### 2.3 非目标（V1 明确不做）

- 自动关闭 CAPA、自动裁定责任方。  
- 完整项目级排程（甘特）、复杂资源优化算法。  
- 替代现有缺陷/CAPA/项目管理系统，仅可做弱关联（外部编号）。

## 3. 用户与场景

### 3.1 角色


| 角色    | 主要职责                              |
| ----- | --------------------------------- |
| 任务发起人 | 多为质量/研发主管或项目经理；录入背景、审阅 AI 草案、确认派发 |
| 承接人   | 执行子任务；必须完成承接确认；按节点反馈              |
| 协作人   | 提供输入、评审或支持；不一定为主责                 |
| 验收人   | 按「完成标准」判定是否完成                     |
| 系统管理员 | 模板、权限、提醒策略配置（可与 IT 兼任）            |


### 3.2 首期覆盖场景（质量 + 研发）

#### 3.2.1 质量域（示例）


| 子类型（示例）  | 典型来源              | 拆解侧重点            |
| -------- | ----------------- | ---------------- |
| 生产/过程异常  | 产线、测试工位           | 遏制、批次范围、工艺/工序接口  |
| 检验/测试异常  | IQC/IPQC/OQC、研发测试 | 复测范围、方法、样本、失效模式  |
| 客诉/售后    | 客户现场、退回品          | 影响评估、复现条件、临时沟通策略 |
| 供应商问题    | 来料、制程审核           | 供应商调查、隔离、纠正措施接口  |
| 设计相关质量任务 | 设计缺陷线索            | 与设计变更、验证、风险更新衔接  |


底层拆解骨架建议对齐 **8D/CAPA 思路**（事实确认 → 遏制 → 根因 → 纠正 → 验证关闭），**但不等同于**公司正式 CAPA 表单；正式记录流程遵循现有质量体系。

#### 3.2.2 研发域（示例）


| 子类型（示例）   | 典型触发      | 拆解侧重点           |
| --------- | --------- | --------------- |
| 需求/设计输入落地 | 评审遗留项     | 需求条目、假设、约束、验收口径 |
| 方案开发与论证   | 系统/软硬件/结构 | 备选方案、风险、验证策略接口  |
| 验证与确认任务   | V&V 计划缺口  | 追溯需求/风险、方法、通过准则 |
| 设计变更行动项   | ECN/变更评审  | 影响范围、回归验证、文档更新  |


研发类任务强调 **范围边界（in-scope / out-of-scope）** 及与**需求/风险**的追溯字段（若公司有编号体系则关联；若无则 V1 可为可选）。

## 4. 核心概念：任务包（Task Package）

每个子任务以统一结构描述，避免「只有标题和截止日期」。

### 4.1 字段定义（最小必填）


| 字段       | 质量域    | 研发域    | 说明                 |
| -------- | ------ | ------ | ------------------ |
| 子任务名称    | 必填     | 必填     | 一句话说明做什么           |
| 任务目标     | 必填     | 必填     | 与上一级目标的承接关系        |
| 范围边界     | 建议     | **必填** | 做什么 / 不做什么         |
| 推荐负责人    | 必填     | 必填     | 可由 HR 能力清单推荐，发起人可改 |
| 协作人      | 选填     | 选填     | 需提供输入或评审的角色        |
| 输入材料     | 必填     | 必填     | 开工前必须具备的资料/样品/权限   |
| 执行动作     | 必填     | 必填     | 阶段级或步骤级            |
| **交付物**  | **必填** | **必填** | 可列举的具体产出           |
| **完成标准** | **必填** | **必填** | 可验证的通过条件           |
| **时间节点** | **必填** | **必填** | 开始、检查点、截止          |
| **反馈频率** | **必填** | **必填** | 如每日/隔日/节点          |
| 验收人      | 必填     | 必填     | 谁判定完成              |
| 风险与待确认项  | 建议     | 建议     | 卡点、需决策点            |
| 追溯信息     | 选填     | 建议     | 需求 ID、风险项、适用标准条目等  |


### 4.2 派发门禁（质量与研发一致）

在发起人确认派发前，系统校验：若缺少 **交付物、完成标准、时间节点、反馈频率** 四项之一，则**默认阻止派发**或要求发起人执行「显式豁免」（豁免原因必选，便于审计；具体策略由管理层与 IT 配置）。

## 5. 端到端流程（业务视角）

```text
发起 → 输入质检（追问缺失信息）→ 场景分类与模板 → WBS 草案
→ HR 人岗推荐（可改）→ 发起人审阅 → 派发
→【强制】承接人：确认 / 修改 / 无法承接 → 发起人汇总修订（如需）
→ 执行中节点反馈（进展 + 证据 + 风险）→ 验收 →（可选）任务定义复盘
```

### 5.1 承接确认（强制）

每位主责承接人必须选择其一：


| 选项   | 承接人需补充的内容                  |
| ---- | -------------------------- |
| 确认承接 | 确认理解目标、交付物与完成标准、时间节点可达成    |
| 需要修改 | 明确指出哪一项不清晰/不合理，缺何输入，建议如何调整 |
| 无法承接 | 原因、冲突任务、能力不匹配点、建议替代人选（若有）  |


**不允许沉默承接**：超时未操作则提醒承接人，再超时升级提醒发起人。

### 5.2 节点反馈（非空洞催办）

按任务类型推送不同结构化问题（示例）：

- **根因类**：当前假设树、已验证/已排除项、证据、下一步最小验证实验。  
- **验证类**：方法、样本、判定准则、当前结果与偏差。  
- **方案类**：备选方案比较、未决决策、需评审资源。

| 类别     | 要求                            |

| 权限与可见性 | 仅相关人员可查看计划与附件；遵循钉钉组织权限        |

| AI 可控性 | 模板化 + 人工确认；模型与提示词版本化管理        |

## 9. 与质量 / 研发体系的协作约定

### 9.1 质量部关注点

- 任务骨架对齐现有 **NCR/CAPA/8D** 口语习惯即可，**正式编号与关闭权限仍在 QMS**。  
- 「遏制、根因、纠正、验证」类子任务建议默认出现在合适子类型模板中，可由质量代表评审模板文案。  
- 证据反馈字段与现场记录习惯对齐（照片、批次、检验记录编号等）。

### 9.2 研发部关注点

- 研发模板默认带 **范围边界**；若有 **需求/风险** 编号规范，在 FR 中升级为「建议必填」。  
- 方案/验证类任务默认追问：**验证对象、方法、样本、通过准则**。  
- 与设计评审、变更流程的接口：V1 **弱关联**（链接或 ID）；深度集成放到后续版本。

| ---- | ---------------------------------------------------------- |
| MVP  | 钉钉机器人 + 质量 2～3 子类型 + 研发 2 子类型 + HR 推荐 + 强制承接 + 节点反馈 + 派发门禁 |

## 11. 风险与缓解


| 风险       | 缓解措施                             |
| -------- | -------------------------------- |
| 表单负担过重   | 短模板、支持语音/粘贴纪要自动抽取字段（后续）；强调减少返工收益 |
| AI 输出不可靠 | 模板约束 + 发起人必审 + 承接人可拒接            |
| HR 数据滞后  | 展示能力清单更新日期；主管可覆盖推荐               |
| 与现有流程两张皮 | 制度上明确：本机器人为协作层，正式记录仍走 QMS        |

## 12. 待决策事项（需质量 / 研发 / 管理层确认）

1. **派发门禁**：四字段缺失时是「硬阻止」还是「可选豁免 + 必填豁免原因」？
2. **质量子类型优先级**：首期上线哪几类（如仅「生产异常 + 测试异常」）？
3. **研发是否强制关联需求/风险 ID**：有无系统字段可供接口？
4. **HR 能力清单字段标准**：领域、产品线、工具（FMEA/8D 等）、角色偏好是否已定？
5. **验收权**：是否一律要求独立验收人，还是允许「主责自验 + 主管抽检」规则表？
