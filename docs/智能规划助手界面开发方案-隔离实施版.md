# 智能规划助手界面开发方案（隔离实施版）

> 文档状态：已批准实施；开发、验证与上线结果以本次提交和部署记录为准
> 目标页面：`/workbench/manager/chat`
> 设计依据：用户确认的智能规划助手截图（未分配草案、分配完成与发放检查两个状态）
> 核心约束：本次只开发“智能规划助手”栏目，不改变其他模块的页面、权限、数据和业务行为。

## 1. 目标结果

把现有智能规划助手改造成“对话 + 可视化任务草案 + 发放检查”的单页协作界面。

主管在同一个页面内完成：

1. 查看会话历史和当前任务背景。
2. 与助手对话拆解任务、调整期限和指定负责人。
3. 通过纵向任务卡确认目标、交付物、完成标准、期限和负责人。
4. 查看任务完整性和发放条件。
5. 通过现有发放链路完成预检和最终确认。

本方案不建立新的任务系统。正式任务、负责人、期限、承接和状态继续以现有工作台 SQLite 和现有业务接口为唯一权威源。

## 2. 不可突破的范围边界

### 2.1 本次允许修改的功能范围

- 仅修改智能规划助手页面 `/workbench/manager/chat` 的页面内部布局和交互。
- 仅处理该页面使用的会话历史、消息展示、草案卡片、负责人快捷选择、发放检查和响应式样式。
- 复用现有会话、草案、通讯录、Agent 和发放接口。
- 新增测试时，仅新增或补充智能规划助手相关测试。

### 2.2 本次明确禁止修改的模块

- 工作台公共顶部栏、左侧主导航和页面框架。
- “切换工作台”以及管理员选择角色、选择具体成员的功能。
- 管理员、主管、员工的角色识别、权限范围和会话模拟逻辑。
- 管理员运营看板、权限中心及其他管理员页面。
- 主管的历史任务、周度 Dashboard、项目总览、会议入库、任务快录入库等栏目。
- 员工的待承接、进行中、已完成、任务详情和进度提交页面。
- 质量追踪列表、质量研判、质量初析、责任链、证据和终验页面。
- 现有数据库表、字段、迁移脚本和正式任务状态机。
- 钉钉 Stream、机器人编排器、Prompt、工具注册表和角色路由。
- 现有通知、催办、进度推送和钉钉待办逻辑。

### 2.3 共享文件保护规则

以下文件默认为“禁止修改”：

- `src/web/workbench-shell.ts`
- `src/web/workbench-admin-impersonation.ts`
- `src/web/admin-workbench-pages.ts`
- `src/web/quality-tracking-page.ts`

如果实现阶段发现必须修改共享文件，开发必须暂停，先提交修改原因、具体行级范围、影响分析和替代方案，得到用户明确确认后才能继续。

## 3. 设计原则

### 3.1 聊天是主流程，表格是辅助工具

- 默认进入聊天页面，不自动弹出草案表格。
- 草案以纵向任务卡展示，不使用十列横向表格作为第一屏。
- 现有“编辑草案表格”继续保留，但只在主管主动点击时打开。
- 已经明确携带 `openDraftEditor=1` 的历史深链保持原行为，避免影响任务快录入库等现有入口。

### 3.2 普通任务与质量任务使用同一界面

- 普通任务：正常打开智能规划助手，不显示质量来源卡。
- 质量任务：只有当前会话存在只读 `sourceContext.kind = quality_event` 时，显示质量事件交接卡。
- 主管不需要手动切换任务类型。
- 质量任务只增加只读背景，不在智能规划助手中建立第二套分配、状态或人员数据。

### 3.3 所有变更以服务器结果为准

- 页面不在本地伪造“已指派”“已修改”或“已发放”状态。
- 负责人和期限调整必须经过现有会话接口，由 Agent 和后端校验后重新读取草案。
- 前端发放检查用于提示，后端 FSM 和现有发布门禁仍是最终判定者。

## 4. 页面整体结构

桌面端参考截图采用三栏布局，但只作用于智能规划助手页面内容区，不改工作台公共外壳。

```text
┌──────────────── 智能规划助手栏目内容区 ─────────────────┐
│                                                        │
│  会话历史区          对话与任务草案区          分配摘要区 │
│  220–260px           自适应主区域              240–290px │
│                                                        │
│  新规划会话          会话标题/任务来源          任务数量   │
│  主线程              只读背景卡（按需）         指派进度   │
│  侧会话列表          对话消息                   总期限     │
│                      纵向任务卡                 发放检查   │
│                      消息输入框                 主操作按钮 │
│                                                        │
└────────────────────────────────────────────────────────┘
```

### 4.1 左栏：会话历史

- 保留“新规划会话”。
- 展示主线程与侧会话，当前会话有明确选中态。
- 每条会话显示标题、更新时间和一行摘要。
- 现有重命名、删除侧会话行为保持不变。
- 不新增全局导航，也不替代工作台原来的左侧主导航。

### 4.2 中栏：对话与任务草案

从上到下包含：

1. 会话标题和主线程/侧会话标记。
2. 可选的只读任务来源卡。
3. 主管与助手的对话消息。
4. 当前草案的纵向任务卡。
5. 固定在中栏底部的消息输入区。

页面只保留一个主要纵向阅读方向。任务背景、对话和任务卡不得被塞入窄侧栏。

### 4.3 右栏：分配摘要与发放检查

右栏不编辑业务数据，只展示当前草案的实时摘要：

- 任务数量。
- 已指定负责人数量，例如 `2/3`。
- 最近截止时间或总期限。
- 负责人是否完整。
- 期限是否完整。
- 交付物是否完整。
- 完成标准是否完整。

底部保留两个操作：

- “编辑草案”：主动打开现有草案编辑器。
- “确认分配并发放”：进入现有两步预检和确认流程。

截图中的“发布”在正式产品文案中统一使用现有口径“发放”。

## 5. 页面状态设计

### 5.1 状态 A：空会话

- 中栏显示欢迎语和可直接使用的示例指令。
- 右栏显示“暂无草案”，不显示发放按钮。
- 普通任务入口不显示任何质量字段。

### 5.2 状态 B：已生成草案、负责人未完整

- 中栏显示任务卡，每张卡明确标记“待指定负责人”。
- 右栏显示任务数量、指派进度和总期限。
- “确认分配并发放”不可直接执行，并说明还缺少哪些字段。
- 主管可通过对话指定人员，也可点击任务卡上的“选择人员”。

### 5.3 状态 C：草案已调整、负责人完整

- 任务卡展示负责人头像/姓名、截止时间、交付物和完成标准。
- 本轮被调整的字段显示短暂的“已调整”标记。
- 右栏的完整性检查逐项变为通过状态。
- 主按钮可进入发放预检。

### 5.4 状态 D：发放预检

- 页面通过现有会话接口请求 Agent 对当前草案执行发放预检。
- 预览内容继续展示在对话区。
- 如果后端返回缺失项，右栏同步展示缺失原因，主按钮返回不可发放状态。
- 预检通过后显示最终确认弹窗。

### 5.5 状态 E：发放完成

- 展示现有后端返回的正式任务编号和发放结果。
- 当前草案切换为已发放状态，禁止重复点击。
- 仍然使用现有发布后会话轮转和任务入库逻辑。
- 质量任务如果有来源关联，只展示后端返回结果，不由前端自行写关联。

## 6. 任务卡信息结构

每张任务卡必须完整展示以下信息：

- 任务标题。
- 任务目标。
- 交付物。
- 完成标准。
- 截止时间。
- 负责人。

执行动作和前置依赖有内容时在卡片底部折叠展示。不得把关键字段缩成难以辨认的小字，也不得用横向滚动隐藏负责人和期限。

卡片快捷操作遵循以下规则：

- “选择人员”复用现有 `GET /api/workbench/manager/contacts` 通讯录搜索。
- 选择确认后，不直接在浏览器篡改草案；页面向现有 `POST /api/workbench/conversation/send` 发送明确的指派要求。
- Agent 返回成功后重新读取 `GET /api/workbench/conversation/draft`，再更新卡片。
- 截止时间快捷调整同样通过现有对话链路提交，第一版不新增直接改库接口。

## 7. 只读质量事件上下文

当现有会话返回 `sourceContext.kind = quality_event` 时，中栏顶部显示可折叠的只读交接卡：

- 质量事件编号和标题。
- 来源事实摘要。
- 质量初析。
- 建议责任部门。
- 处理要求。
- 建议总期限。
- 来源版本和关联状态。

该卡只负责显示上下文，禁止在其中选择具体负责人、修改质量结论、改变事件状态或写入质量数据库。

没有 `sourceContext` 时整个卡片不渲染，不保留空白区域，因此普通任务流程和当前界面语义不受影响。

## 8. 现有接口复用方案

第一版不新增数据库表，不新增正式任务接口，优先复用：

- `GET /api/workbench/conversation/threads`：会话列表。
- `POST /api/workbench/conversation/new`：新建侧会话。
- `PATCH /api/workbench/conversation/thread`：重命名侧会话。
- `DELETE /api/workbench/conversation/thread`：删除侧会话。
- `GET /api/workbench/conversation/messages`：消息、会话元数据和可选只读来源上下文。
- `GET /api/workbench/conversation/draft`：草案、指派关系和编辑行数据。
- `POST /api/workbench/conversation/send`：对话调整、点将、预检和最终确认。
- `POST /api/workbench/conversation/draft/revise`：现有草案编辑器提交。
- `GET /api/workbench/manager/contacts`：真实通讯录搜索。
- `POST /api/workbench/manager/upload-roster`：现有花名册上传。

如果旧版基线缺少某个只读响应字段，只允许给现有响应增加向后兼容的可选字段；不得借机修改其他页面的接口形态或业务状态。

## 9. 隔离式代码组织

实现时优先新建智能规划助手专用文件，避免继续扩大共享文件：

- `src/web/manager-chat-page.ts`：只负责智能规划助手页面结构。
- `src/web/manager-chat-page-styles.ts`：只输出页面专用样式，所有选择器统一加 `.manager-chat-v2` 前缀。
- `src/web/manager-chat-page-client.ts`：只处理本页面会话、草案卡片、通讯录选择和发放检查。
- `tests/web/manager-chat-page.test.ts`：页面结构和状态测试。
- `tests/web/manager-chat-isolation.test.ts`：禁止影响其他页面的隔离测试。

现有路由文件只允许进行最小接线：让 `/workbench/manager/chat` 使用新的页面渲染器。不得在同一提交中改造其他路由。

如果最终决定暂不拆文件，则只允许修改 `renderManagerChatPage` 函数内部，不能修改同文件中的历史任务、质量任务或其他主管页面函数。

## 10. 开发实施顺序

### 阶段 0：冻结旧版基线

1. 以当前已回滚的旧版行为作为功能基线。
2. 保存管理员成员切换、主管任务页、员工任务页、质量追踪页和智能规划助手的基线截图。
3. 记录旧版镜像 `manage-robot:dingtalk-a1e0e9c`，作为线上快速回滚目标。
4. 开发分支不得从包含错误全局改造的分支直接继续开发。

### 阶段 1：新建独立 HTML 交互原型

1. 新建原型文件，不覆盖现有原型和源码。
2. 还原截图的三栏结构及两个核心状态。
3. 验证 `1366×768` 和 `1920×1080`。
4. 用户确认原型后才能进入正式页面开发。

### 阶段 2：只读页面骨架

1. 接入现有会话列表和消息接口。
2. 接入现有草案接口并渲染任务卡。
3. 接入只读分配摘要和完整性提示。
4. 此阶段不允许产生任何新的业务写操作。

### 阶段 3：页面内交互

1. 复用现有消息发送和通讯录搜索。
2. 实现负责人快捷选择后通过对话链路提交。
3. 保留花名册上传和表格编辑器。
4. 确保质量来源卡只读。

### 阶段 4：发放预检和确认

1. 复用现有预检消息和确认消息。
2. 防止重复提交。
3. 后端失败时保留当前草案并给出可恢复提示。
4. 不改变现有 publish gate、审计和通知逻辑。

### 阶段 5：回归、评审和部署

1. 完成智能规划助手专项测试。
2. 完成其他模块不变的隔离回归。
3. 提交新旧页面对比截图给用户评审。
4. 用户明确确认后才允许推送和部署。

## 11. 响应式规则

### 11.1 宽屏，视口宽度不小于 1600px

- 三栏完整显示。
- 左栏约 260px，右栏约 280px，中栏占剩余空间。
- 任务卡一行展示负责人、期限、交付物和完成标准。

### 11.2 标准桌面，视口宽度 1200–1599px

- 三栏继续保留，但左右栏收窄。
- 任务卡内容允许分成两行，不允许出现横向滚动条。
- 输入框和主按钮高度不少于 42px。

### 11.3 窄屏，视口宽度小于 1200px

- 会话列表变为抽屉。
- 右侧摘要折叠为中栏顶部摘要条或底部抽屉。
- 中栏成为唯一主视区。
- 不改变桌面版的信息字段，只改变排列方式。

## 12. 视觉规范

- 延续现有工作台的白底、浅灰边框和蓝色主操作，不重做全局视觉语言。
- 页面标题使用现有字号体系，不修改公共导航字体。
- 任务卡使用轻边框和清晰间距，不使用大面积渐变、强阴影或过多彩色卡片。
- 正文和输入内容不小于 14px，辅助信息不小于 12px。
- 主要按钮和输入控件高度至少 42px。
- 多行背景和任务描述行高保持在 1.65 左右。
- 警告使用文字加图标，不只依赖颜色表达。

## 13. 测试与“不影响其他模块”门禁

### 13.1 智能规划助手专项测试

- 普通任务打开时不显示质量来源卡。
- 质量会话存在只读上下文时正确显示来源卡。
- 空会话、未完整指派、完整指派、预检中、发放完成五种状态正确。
- 任务卡字段不会错位、截断成错误值或全部显示同一内容。
- 通讯录选择后必须等待后端返回，不能前端伪造成功。
- 表格编辑器不会在普通进入和质量进入时自动弹出。
- 显式 `openDraftEditor=1` 的既有深链仍可工作。
- 发放按钮具备防重复提交。

### 13.2 其他模块不变回归

以下页面在开发前后必须进行相同账号、相同数据的截图和行为对比：

- 管理员“切换工作台”及多角色、具体成员选择。
- 管理员运营看板和权限中心。
- 主管历史任务、周度 Dashboard、项目总览、会议入库和任务快录入库。
- 员工待承接、进行中、已完成和任务详情。
- 质量追踪列表、事件详情和质量处理页面。

任何一项出现 DOM、接口、权限、数据范围或视觉差异，均视为本次开发不合格，不允许部署。

### 13.3 文件变更门禁

提交前执行 `git diff --name-only`，结果必须仅包含：

- 本方案批准的智能规划助手专用文件。
- 智能规划助手专项测试。
- `/workbench/manager/chat` 的最小路由接线。
- 经用户单独确认的其他文件。

发现未授权文件变更时必须停止提交，不能以“共用样式”或“顺手优化”为理由一起发布。

### 13.4 必须执行的验证

- TypeScript 类型检查。
- 智能规划助手相关 Vitest。
- 工作台完整测试集。
- `1366×768` 与 `1920×1080` 页面截图对比。
- 普通主管、项目主管、管理员模拟主管三种进入方式。
- 微光与明思两个实例的环境隔离检查。

## 14. 部署与回滚约束

- 文档评审和原型评审完成前，不推送、不部署。
- 构建新镜像时使用独立版本标签，不覆盖旧镜像。
- 部署前分别备份两个实例的 SQLite。
- 先在单个实例验证智能规划助手，再决定是否更新另一个实例。
- 部署后同时检查公网健康接口、钉钉 Stream 和智能规划助手页面。
- 发现其他模块变化时立即回滚，不在生产环境继续修补。
- 快速回滚目标保留为 `manage-robot:dingtalk-a1e0e9c`，数据卷和 env 保持不变。

## 15. 验收标准

满足以下全部条件才算完成：

1. 智能规划助手页面效果与参考截图的核心结构一致。
2. 主管可在同页完成对话、查看任务卡、点将、调整和发放确认。
3. 普通任务不出现质量信息，质量任务只显示只读来源信息。
4. 任务卡完整展示目标、交付物、完成标准、期限和负责人。
5. 默认不自动打开横向草案表格。
6. 发放仍经过现有后端门禁、审计、入库和通知流程。
7. 不新增第二套任务状态或数据库。
8. 管理员多角色和具体成员切换与旧版完全一致。
9. 主管、员工、质量追踪及其他工作台栏目无功能和视觉变化。
10. 用户查看对比图并明确确认后，才允许部署上线。

## 16. 本次明确不做

- 不重做整个工作台。
- 不修改导航和角色视角。
- 不修改质量追踪页面。
- 不新建质量任务分配状态机。
- 不改变正式任务表结构。
