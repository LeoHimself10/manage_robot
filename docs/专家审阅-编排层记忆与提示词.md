## 1. 单次请求的完整消息栈（可复现）

`runOrchestrator()` 组装 OpenAI-compatible messages，顺序固定：

```
[0] role=system     → buildQwenPlannerSystemPrompt(profile, { managerFollowup? })
[1] role=assistant  → "[memory_context]\n..." （有 session 状态时）
[2..N-1]            → conversationHistory 最近 AGENT_HISTORY_TURNS 条（默认 10）
[N] role=user       → 本轮用户原文
```

**代码位置**：`orchestrator.ts` L151–278

### 1.1 示例：主管第二轮 DRAFT（含 memory_context）

假设 `planId=plan-abc`，已有 2 条 knownFacts，尚无 draft：

```json
[
  {
    "role": "system",
    "content": "promptVersion: orchestrator-agent-v5.23.8\n## 角色与流程\n..."
  },
  {
    "role": "assistant",
    "content": "[memory_context]\nplanId: plan-abc\nmemorySummary: planId=plan-abc; lastTraceId=trace-001\ncurrentTime: 2026-05-21T09:00:00.000Z\ntopFacts: [\"deadline:2周内\",\"型号:A100 OCT导管\"]\npostClarifyDraftAction: 用户已在 CLARIFY 后补充信息；本轮走 DRAFT，遵守 system 中 DRAFT 四段 message + draft.title/description/tasks[]，禁止空 message；**禁止** search_employees。"
  },
  {
    "role": "user",
```

## 2. ReAct 循环（`callWithTools`）— 精确行为

**文件**：`src/agent/demo/qwen-compatible-client.ts`

| 参数 | 默认值 | 环境变量 |
|------|--------|----------|
| maxIterations | 6 | 构造 OrchestratorConfig 时 `maxToolIterations` |
| maxTotalMs | 120000 | `AGENT_MAX_TOTAL_MS` |
| maxToolCalls | 12 | `AGENT_MAX_TOOL_CALLS` |
| maxTotalTokens | 12000 | `AGENT_MAX_TOTAL_TOKENS` |

**每轮 iteration**：

1. POST `/chat/completions`（DashScope OpenAI 兼容），带 `tools[]`
2. 若 `choices[0].message.tool_calls` **为空** → `parseAssistantJsonPayload(content)` → **return**（结束循环）
3. 若有 tool_calls：
   - 把 assistant message（含 tool_calls）push 进 messages
   - **并行**执行 `isParallelSafeTool(name)===true` 的工具
   - **串行**执行 `update_known_facts` 等非 parallel-safe 工具（`save_draft` 仍保留于实现但不对任何 profile 开放）
   - 每个 tool result 以 `role=tool` push 回 messages
   - 若本轮含 `start_new_task` / `switch_back_task` ok → `applyScopeSwitchToRuntimeMessages()` 截断历史
4. iteration++，回到 1；超过 maxIterations → 抛 `MaxToolIterationsExceededError`

**伪模式名误调**：模型若 tool_call 名为 `CLARIFY`/`DRAFT`/`PUBLISH` 等 → 不 throw，返回：

```json
{
  "ok": false,
  "error": "mode_not_a_tool",
  "mode": "DRAFT",
  "hint": "DRAFT 是输出模式标签，不是可调用的 function。请停止 tool_calls，直接返回 JSON（message 或 message+draft）。"
}
```

伪模式集合（L961–970）：`CLARIFY, QUERY, DRAFT, ASSIGN, PUBLISH, FOLLOWUP, PREPARE, REVISE`

**超时/超轮 salvage**（`orchestrator.ts` L293–347）：

- 从 `savedDraft`（工具回调 `onDraftSaved`）或最后一轮 assistant content 解析 JSON
- 用户可见 fallback 由 `buildOrchestratorInterruptMessage()` 生成，**明确写「流程中断，不是你没提供信息」**

## 3. `[memory_context]` 注入规则（逐条、带触发条件）

**组装函数**：`runOrchestrator()` L155–266  
**原则**：主要由 **session 状态** 驱动；仅 3 处扫描用户正文：

| hint 键 | 触发条件（代码） | 注入文案（摘要） |
|---------|------------------|------------------|
| `planId` | `sessionContext.planId` 存在 | `planId: {id}` |
| `memorySummary` | 非空 | SQLite summary 或 `planId=...; lastTraceId=...` |
| `currentTime` | 非空 | ISO 时间 |
| `topFacts` | `memoryFacts.length>0` | JSON 数组，**最多 8 条** |
| `latestDraftSummary` | `latestDraft` 存在 | 见 §3.1 |
| `publishedTasksLookup` | 有 latestDraft 时**固定**附带 | 禁止用 draft 冒充已发布任务 |
| `publishStaging` | `draft.stagedBy==="prepare_publish_task"` | `{staged:true,...}` |
| `latestAssignmentSummary` | `latestAssignment` 存在 | `{hasAssignment, taskIds[]}` |
| `pendingRoster` | 主管上传名单未消费 | ACTION_REQUIRED: read→search→set_candidate_pool |
| `scopeBoundary` | `scopeRotatedSinceLastTurn` 非空 | 禁止引用旧 scope task_x/人名 |
| `candidatePool` | pool 存在 | entries brief + 指派只能在池内 |
| `firstTurnDraftAction` | `awaitingFirstDescribe && !hasPublishableDraft && hasDeadlineInKnownFacts` | 必须 DRAFT |
| `firstTurnClarifyAction` | 同上但 **无** deadline fact | CLARIFY-only |
| `rosterAssignAction` | 有 draft + pool + **无** assignment | 走 ASSIGN |
| `explicitDraftRequest` | 用户匹配 `/请?\s*生成(正式)?草案\|出草案\|.../i` 且有 deadline | 必须 DRAFT |
| `explicitDraftRequestButMissingDeadline` | 同上但无 deadline | CLARIFY-only |
| `postClarifyDraftAction` | 用户消息 **≥120 字** + 无 draft + 上轮 assistant 像 CLARIFY | 必须 DRAFT |
| `publishStagingAction` | `shouldInjectPublishStagingMemoryHint()` | 必须 prepare 或 publish |

`summarizeDraftForPrompt()`（`orchestrator.ts` L476–497）产出：

```json

  "domain": null,
  "subtype": null,
  "stagedBy": "prepare_publish_task",
  "taskFields": [

      "filled": ["objective", "deliverables", "completionCriteria", "feedbackFrequency"],
      "missing": ["dependencyTaskIds", "checkpoints", "risksAndOpenQuestions", "inputMaterials", "actions", "collaborators", "scope"]
    }

```

### 3.2 `knownFacts` 与 deadline 判定

`hasDeadlineInKnownFacts()`（`orchestrator-memory-hints.ts`）对 fact 字符串 **小写 trim** 后，前缀匹配：

- `deadline:`
- `timerange:` / `time_range:`
- `fact:deadline:`
- `due:`

**示例 fact**（模型应通过 `update_known_facts` 写入）：

```
deadline:2周内完成
timerange:2026-06-01至2026-06-30
型号:A100
批号:B2026-03
客诉例数:3
```

**存储上限**：dingtalk-bot 合并时 `slice(-50)`；注入 prompt 时 `slice(0, 8)`。

## 5. 记忆四层 — 读写路径对照

| 层 | 写入者 | 读取者 | 存储 |
|----|--------|--------|------|
| knownFacts | 模型 `update_known_facts` | `[memory_context].topFacts` | PlanSession JSON |
| conversationHistory | dingtalk-bot 每轮 append | ReAct messages | PlanSession JSON |
| SQLite memory | `appendMemoryEvents()` 异步 | `loadMemoryContextForPlan()` → memorySummary + facts | workbench.sqlite |
| plan-index | `savePlanEmbedding()` 于有 draft 时 | `search_similar_plans` 工具 | `{traceId}.embedding.json` |

### 5.1 SQLite memory 表结构

`workbench-memory-store.ts` L267–300：

```sql
memory_summaries(plan_id PK, summary_text, updated_at)
memory_facts(fact_id PK, plan_id, scope_type, scope_id, kind, value_text,
             source_type, confidence, confidence_score, status, dedupe_hash,
             created_at, updated_at, expires_at, superseded_at)
memory_events(id, plan_id, event_type, payload_json, occurred_at)
```

**提取 prompt**（独立 LLM，不进 ReAct）：

```
system: 你是 memory 提取器。只返回 JSON...
        输出结构：{ summary: string, facts: [{ kind, value, source, confidence, expiresAt? }] }
user:   JSON.stringify({ planId, userMessage, assistantMessage, latestDraftSummary, latestAssignmentSummary })
```

- 模型：`MEMORY_EXTRACTION_MODEL`（默认 `qwen-doc-turbo`）
- 每轮最多写 **12 条** facts
- dedupe：`sha256(planId|kind|value)`，重复则 supersede 旧行
- TTL：`MEMORY_FACT_TTL_DAYS`（默认 **14**），过期 status→`expired`

### 5.2 plan-index 检索

- Embedding API：DashScope `text-embedding-v3`
- 本地 cosine，**score > 0.5** 才入选，top **3**
- 空结果 hint：`no_match_in_plan_index_do_not_retry_same_query`

## 6. Backend FSM — 发布链路逐步

### 6.1 状态机

```
[有 latestDraft.tasks + latestAssignment 全指派]
        │
        ▼ 用户说「可以发布/指派好了」（非确认发布短句）
   prepare_publish_task
        │ ok → draft.stagedBy = "prepare_publish_task"
        │      orchestratorTurnFlags.markPrepareCalledThisTurn()
        ▼
   主管单独一条「确认发布」
        │
        ▼
   publish_task → SQLite 正式任务 + 钉钉通知
```

### 6.2 `prepare_publish_task` 返回码

| ok | reason | 含义 |
|----|--------|------|
| false | `search_employees_quota_exhausted` | 本轮 search 已耗尽且点将未完成 |
| false | `missing_plan_id` / `plan_mismatch` | planId 错误 |
| false | `no_draft` | session 无 tasks |
| false | `missing_description` | 无 description/summary |
| false | `missing_assignee` | latestAssignment 未齐 |
| false | `invalid_assignee_user_id` | userId 不在通讯录 |
| true | `already_staged` | hash 未变，跳过重复 prepare |
| true | （正常） | 写入 stagedDraft + stagedAssignment |

成功后 `latestDraft` 增加字段：`stagedBy`, `stagedAt`, `stagedDraftHash`, `stagedAssignmentHash`

### 6.3 `publish_task` 硬阻断

**同轮 prepare 后立刻 publish**（`publish-task.ts` L149–157）：

```json
{
  "ok": false,
  "reason": "must_confirm_separately",
  "hint": "prepare_publish_task 与 publish_task **必须分两轮**..."
}
```

**prepare 后 draft/assignment 被改**（L159–166）：`reason: "stale_staging"`

**其他软返回**：`no_draft_in_session`, `missing_assignee`, `alreadyPublished`, `dedupedByLru`

### 6.4 用户「确认发布」短语识别

`isPublishConfirmUserMessage()`（`publish-staging.ts` L25–36）：

- 长度 **≤30** 字
- **排除**：`/再改|等等|取消|暂缓|别发|.../i`
- **排除**：`/确认.{0,8}(分配|负责人|名单|人选)/`（仅分配确认）
- **命中示例**：`确认发布`、`发布吧`、`发布`、`看着可以`、`没问题`、`确定`、`OK`

### 6.5 假发布检测（仅审计，当前无自动重试）

dingtalk-bot L893–920：`detectFalsePublish` || `detectFalsePublishOnConfirm` → 打 `false_publish_observed` 日志  
**注意**：与 scope/draft 混写不同，假发布 **不再** 自动 `buildPublishRetryUserMessage` 重试（函数仍存在于 `publish-staging.ts` 供测试/备用）

## 7. dingtalk-bot 后置守卫重试链（严格顺序）

每轮用户消息，**最多 1+4 次** `runOrchestrator` 调用：

| 顺序 | 检测函数 | 条件摘要 | 重试 user 消息前缀 | 审计 event |
|------|----------|----------|-------------------|------------|
| 0 | — | 首次 | 用户原文 | — |
| 1 | `detectFalseScopeSwitch` | outbound 含 `/已归档\|已切(换\|到新任务)\|.../` 且未调 `start_new_task` | `[scopeSwitchAction]` | `scope_switch_silent_skip_*` |
| 2 | `detectTopicSwitchWithoutArchive` | 有 preTurnDraft + 用户含 `/换个\|新任务\|.../` + 未调 start_new_task | `[scopeSwitchAction]` | `topic_switch_without_archive_*` |
| 3 | `detectDraftClarifyMix` | 有 draft + message 含 `/等待补充\|请补充\|以便我生成.../` | `[draftClarifyMixAction]` | `draft_clarify_mix_*` |
| 4 | `detectDraftNeedsFinalize` | 调了 `update_draft_task` 但无顶层 draft JSON | `[draftFinalizeAction]` | `draft_finalize_*` |
| 5 | `detectFalsePublish*` | 仅 **log**，不重试 | — | `false_publish_observed` |

**重试时 conversationHistory 仍记用户原文**（retry 背景塞给 orchestrator 的 `[scopeSwitchAction]` 等 **不** 写入 history）

- CLARIFY/无 draft 时：`allowSearchBeforeDraft()` 为 false → 拒绝（除非有 candidatePool / pendingRoster）

## 10. 模型与输出后处理

### 10.1 默认模型策略

`model-policy.ts`：`qwen3.6-plus`, temperature=0.2, maxTokens=4000, timeoutMs=60000  
线上常用 override：`QWEN_MODEL=qwen3.6-flash`；钉钉默认 `DINGTALK_QWEN_THINKING=0`

### 10.2 orchestrator 输出管线

```
LLM JSON payload
  → savedDraft ?? payload.draft
  → preserveOrchestratorDraftScalars(raw, coerceLlmPlanPayload(raw))
  → stripPlanningPersonFieldsFromDraft()   // 去掉 tasks[].assigneeUserId 等
  → stabilizeDraftTaskIds(draft, previousDraft)  // 保持 task_1, task_2 稳定
```
